# Sarathi dashboard functionality audit — 7 October 2026

## Verdict

**Both dashboards are visible and their main screens load, but the apps are not fully correct.** Several confirmed defects were repaired during this audit. Important accounting calculation and company-permission defects remain. Do not interpret successful rendering or passing structural tests as certification of every business result.

Tested the local Docker site `frontend` at `http://localhost:8080`, not a remote production deployment.

## Repairs made and verified

1. **Customer-filter isolation:** an empty customer selection fell back to company-wide Job Cards. BOM and stock detail selection also admitted unrelated records. The selected customer/project now constrains these datasets. Existing isolation tests pass.
2. **BOM submission lifecycle:** the generic event-registration loop overwrote `on_bom_submit`, preventing automatic assignment of the first submitted BOM to its project. Restored the lifecycle handler, which already sends its own refresh notification. Transactional BOM tests now pass.
3. **Record drill-down scope:** `get_record` fell back to an unrestricted document fetch when a record was absent from the selected dataset. Removed that fallback and added explicit document read permission enforcement. Cross-project BOM detail rejection now passes.
4. **Executive report execution:** Gross and Net Profit Report lacked financial-statement period filters; Financial Ratios lacked fiscal-year/periodicity defaults. Browser testing also found wrong project-filter types for AR/financial statements and a wrong field name for Project Summary. Added native filter mappings and excluded dashboard-only search arguments. All nine executive reports and the affected selected-project cases now execute without an error payload in regression tests.
5. **Owner endpoint access:** context, home summary and page-data endpoints lacked owner-role rejection. Added it and regression coverage. This addresses missing role checks, **not** all company/document-level scoping issues below.
6. **Report controls:** changing the report now updates the “Desk” link. Owner date presets now populate report date filters. Balance Sheet is included in the financial-report role gate.
7. **Realtime invalidation:** removed immediate duplicate publications and record identities from broad dashboard notifications. Refresh signals now wait for commit; regression coverage checks this behavior.

The local backend was restarted to load the changes. No remote deployment or commit was made. Business test fixtures were rolled back; browser audit sessions were revoked after use. No business invoices, payments or manufacturing orders were submitted as part of browser testing.

## Remaining confirmed issues

### High: company restrictions are bypassed by financial aggregation and owner options

A temporary user with Accounts User and Sarathi Owner roles was restricted to one company. The live probe established all three conditions:

- Frappe denied read access to the other company.
- `get_owner_context()` still included that company in its returned options.
- `get_accounting_card_summary()` still returned that company's nonzero revenue.

Relevant code: `sarathi_owner/sarathi_owner/api/owner_dashboard.py` (`get_owner_context`, plus widespread aggregate `get_all` calls); `sarathi_visibility/sarathi_visibility/api/accounting.py` (`_check_read`, `_sum_field`, raw SQL aggregations).

DocType-level read permission is insufficient for Company/User Permission restrictions. All affected aggregation queries and option loaders need consistent document/company scoping, including when the company filter is blank. The main industrial `load()` path already checks selected links, but that does not establish that every finance aggregate is scoped.

### High: accounting analytics presents assumptions as live results

In `sarathi_visibility/sarathi_visibility/api/accounting.py`:

- A valid zero GL revenue/expense result is replaced with invoice grand totals. A controlled probe returned revenue **118** for an empty GL result because the invoice fallback supplied 118. Zero is a valid ledger result; invoice grand totals also have different meaning from ledger income/expense.
- The invoice-expense fallback assigns costs as **70% COGS / 30% operating expense**, without transaction-level classification.
- If no approved budget is found, a budget is generated as **actual expense × 1.35**.
- “Committed” expense is **total expense × 0.1**, rather than outstanding purchasing commitments.
- Average monthly revenue divides by **6**, irrespective of the selected reporting period.
- Several month-end review checklist items are hard-coded complete or inferred merely from balances/account existence; this does not prove a review or reconciliation happened.

These are implementation findings, not validated live business measurements. Replace them with source-backed calculations or clearly display unavailable/estimated status.

### High: budget summary and detailed calculations disagree

The live summary returned **0% budget used**, while the detailed accounting view returned **128%** for the same company/month. The summary queries legacy `Budget Account` rows and suppresses exceptions; the detail supports the installed Budget fields. The detail also takes absolute expense values for utilization while returning signed expense for other budget numbers. Both screens need one definition of actual, approved, committed, available and variance, with the same scope and period.

Negative expense balances exist in the source data. Their business validity was not certified; the audit did not alter accounting entries to make displayed values look normal.

## Data gaps and limits

- Current industrial data contains 7 Work Orders and 15 Job Cards, but no loaded Job Card time logs, BOM operation rows, operation balances, live activity rows or machine integration records. Empty charts/reports can therefore be legitimate empty states. One existing permission-scoped time-log test was skipped for this reason.
- No end-to-end physical machine telemetry, TubePro/CypCut/Tally synchronization or external AI provider conversation was executed. Referenced API imports were checked; importing the agent dependency emitted a Python 3.14/Pydantic v1 compatibility warning.
- No exhaustive save/submit/cancel/delete exercise of every ERPNext DocType or every role was performed on this business site. Transactional tests cover selected validations and lifecycle behavior.
- Initial visual verification used a 1440×1000 desktop viewport. This is not a full device/accessibility certification. Frappe's “Getting Started” overlay was present and can obscure part of the dashboard until dismissed.
- The module launcher is intentionally disabled on the owner dashboard in its current source; its absence there is not classified as a new defect.
- Some API calls were slow during concurrent local audit work (the owner Projects loader took about 23 seconds in the initial sweep). This is not a load-test benchmark; performance under multiple real users remains unverified.

The immediate next repair priority is permission-scoped financial queries, followed by replacing the unsupported financial assumptions and reconciling budget calculations. After those repairs, repeat the financial and restricted-user probes in addition to the existing test suite.
